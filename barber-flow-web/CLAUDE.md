# CLAUDE.md — barber-flow-web

Ver el `CLAUDE.md` raíz del monorepo para contexto cruzado (backend, mobile, deployment). Este archivo cubre únicamente el trabajo de **paridad visual mobile → web** en curso sobre este subproyecto, y sirve de bitácora/checklist para continuarlo en sesiones futuras.

## Contexto

Se está migrando el "look and feel" completo de la app mobile (React Native, la referencia de UX según el `CLAUDE.md` raíz) hacia esta app web, pantalla por pantalla, buscando una copia visual lo más exacta posible: mismos colores, tipografía, íconos, imágenes y estructura de layout — no solo una reskin superficial con los componentes MUI por defecto.

Patrón de trabajo establecido (repetir para cada pantalla nueva):
1. Investigar la pantalla mobile equivalente (`barber-flow-mobile/Barber.Flow.Mobile/src/screens/...` + su theme en `src/theme/themes.ts`) para extraer valores exactos (hex, spacing, radius, copy).
2. Investigar el estado actual de la pantalla web equivalente.
3. Presentar un plan (vía plan mode) antes de tocar código — decisiones de alcance (¿reemplazo total o agregar como vista nueva?, ¿se alinean enums de dominio?, ¿modal o página completa?) se resuelven con el usuario antes de implementar.
4. Implementar reutilizando los tokens de color compartidos (`src/presentation/theme/appColors.ts`).
5. Verificar con `npm run lint` + `npm run build`, y probar en navegador con `claude-in-chrome` usando una sesión real (usuario `admin` / contraseña `password` contra el backend local).

**Bugs preexistentes encontrados y arreglados durante la verificación** (no introducidos por este trabajo, pero bloqueaban probar cualquier hook autenticado):
1. `AxiosHttpClient` no compartía el token JWT entre instancias — cada hook (`useAppointments`, `useClients`, `useReports`) crea su propia instancia de Axios, y `setAuthToken()` solo afectaba a la instancia del login. Se arregló con un interceptor de request que lee el token desde `localStorage` en cada instancia (`src/infrastructure/http/AxiosHttpClient.ts`). Esto probablemente destrababa silenciosamente Clientes y Reportes también — vale la pena confirmarlo al trabajar esas pantallas.
2. El diálogo de editar cita no precargaba los datos porque `useForm` solo toma `initialValues` en el primer montaje y el Dialog nunca se remontaba al cambiar de cita. Se arregló con `key={editingAppointment?.id ?? 'new'}` en `AppointmentForm`.

**Pendiente resuelto en Configuración** (ver más abajo): la comisión % ya no es un placeholder fijo — se resolvió el vínculo `User → Barber` y `MongoDbReportRepository` usa la comisión/gasto real cuando existe.

A diferencia de mobile (que simplemente no monta esos tabs), web además necesita bloquear la navegación directa por URL: nuevo guard `OperationalRoute` (`src/presentation/components/shared/OperationalRoute.tsx`) envolviendo `/appointments`, `/clients`, `/reports` en `Router.tsx`, que redirige a `/dashboard`. Default: activo (bloqueado), igual que mobile.
- `ReportCalculationSettingsCard` — comisión %/gasto fijo del barbero logueado, resolviendo el `Barber` cuyo `userName` calza con la sesión actual (`IBarberRepository.GetByUserNameAsync` en el backend). Si no hay vínculo, muestra estado informativo en vez de un formulario inútil.
- `ApplicationUsersCard` + `ApplicationUsersDialog` (admin-only) — CRUD completo de cuentas de Barbero (crear/buscar/editar/eliminar), como **Dialog** en vez de modal full-screen (mismo criterio que Clientes/Citas). Sin campo de foto (mismo criterio que `ClientForm`, sin infra de upload en web).
- `AboutCard` — versión, desarrollador, link a política de privacidad.

**Cierre del loop de comisión % en Reportes (backend + frontend):** `MongoDbReportRepository` usaba una comisión/gasto hardcodeados (40%/₡0) porque no tenía forma de resolver el barbero del usuario autenticado. Se threadeó el `userName` autenticado desde `ReportsApi` → `IReportService` → `IReportRepository.GetDailyReportAsync` (nuevo parámetro `requestingUserName`), y `MongoDbReportRepository` ahora resuelve el `Barber` vía `IBarberRepository.GetByUserNameAsync` y usa su `Settings` real si existe (con el mismo 40%/₡0 como fallback para cuentas sin `Barber` vinculado, como `admin`). Verificado end-to-end: creado un `Barber` con `userName: admin` y comisión 25%/gasto ₡1,500, una cita completada de ₡10,000 mostró correctamente `commissionAmount: 2500`, `netProfit: 6000` tanto en la API como en la UI de Reportes.

**Bug de backend encontrado y arreglado durante la verificación:** `BarbersApi.UpdateBarberAsync` nunca mapeaba `request.Settings` al construir la entidad para actualizar (a diferencia de `CreateBarberAsync`, que sí lo hacía) — significaba que la comisión de un barbero nunca podía cambiarse después de creado, solo al crearlo. El repositorio Mongo ya tenía `Settings` en su `Update`, el bug estaba solo en el endpoint.

**Restricción de autorización heredada del backend (no introducida por este trabajo):** `BarbersApi` exige que quien llama a create/update/delete sea *exactamente* la cuenta admin configurada (`BARBERFLOW_ADMIN_USERNAME`, default `"admin"`), no simplemente cualquier usuario con rol Admin. Esto significa que `ReportCalculationSettingsCard` (pensado para que cualquier barbero edite su propia comisión) en la práctica solo puede guardar cambios cuando la sesión activa es la cuenta `admin` — mismo comportamiento ya existente en mobile, no es una regresión de este trabajo, pero vale la pena tenerlo presente.

**Modal de confirmación propio (post-verificación en navegador):** al probar el flujo de eliminar en `ApplicationUsersDialog`, se detectó que la confirmación usaba `window.confirm` — un alert nativo del navegador, fuera de línea con el resto de la paridad visual. Mobile ya tenía resuelto este mismo problema con un `DialogContext`/`useDialog().showAlert()` propio (`barber-flow-mobile/.../src/context/DialogContext.tsx`, un `Modal` de React Native estilizado con los tokens del theme). Se portó el mismo patrón a web: `src/presentation/context/ConfirmDialogContext.tsx` (`ConfirmDialogProvider` + hook `useConfirmDialog().confirm({ title, message, confirmText, cancelText, destructive })`, devuelve una `Promise<boolean>`), montado en `App.tsx` junto a los demás providers. Reemplazó los dos usos de `window.confirm` que había en la app: `ApplicationUsersDialog` (eliminar usuario de aplicación) y `ClientsPage` (eliminar cliente). Verificado en navegador: el modal respeta el estilo dorado/oscuro de la app en ambos flujos, y `Cancelar` no ejecuta la eliminación.

### Olvidé mi contraseña / OTP / Reset (`ForgotPasswordForm.tsx`, `VerifyOtpForm.tsx` nuevo, `ResetPasswordForm.tsx`)
`ForgotPasswordPage`/`ResetPasswordPage` eran visualmente MUI-default (Container/Card/Stepper, sin `appColors`) y **funcionalmente stubs** — el submit de email y de OTP en el antiguo `Stepper` de una sola página tenían las llamadas al backend comentadas como `// TODO`, nunca conectadas; `ResetPasswordForm` igual. No existía ruta `/verify-otp`.

**Bug de contrato encontrado y arreglado:** el backend (`AuthApi.cs`) espera un flujo real de **OTP de 6 dígitos por email** (no un link mágico) — `POST /api/auth/verify-otp` y `POST /api/auth/reset-password` requieren el campo `otpCode`, pero los DTOs web (`VerifyOtpRequest`/`ResetPasswordRequest` en `AuthRequests.ts`) usaban `otp`, y `IAuthRepository.resetPassword`/`AuthApi.resetPassword` ni siquiera recibían el código OTP en su firma (`resetPassword(email, newPassword)`) pese a que el backend lo exige junto con el email y la nueva contraseña. Se corrigió la firma a `resetPassword(email, otp, newPassword)` y se alinearon los DTOs de red a `otpCode` (el estado interno de los forms sigue usando `otp` como nombre de variable, igual que mobile — solo el payload de red usa el nombre exacto del backend).

**Se pasó de un stepper de una sola página a 3 rutas separadas**, replicando la estructura real de mobile (`ForgotPasswordScreen` → `OtpVerificationScreen` → `ResetPasswordScreen`, pasando `email`/`otp` por route state) en vez de reimplementar navegación con `Stepper` de MUI:
- `/forgot-password` — solo email, página plana sin hero (igual que mobile, a diferencia del Login que sí tiene hero), llama a `ForgotPasswordUseCase.requestOtp` (ya existía en `src/application/use-cases/auth/ForgotPasswordUseCase.ts`, solo hacía falta conectarlo) y navega a `/verify-otp`.
- `/verify-otp` (pantalla nueva, no existía en absoluto) — 6 inputs de 1 dígito con auto-avance/backspace/auto-submit calcado de `OtpVerificationScreen.tsx`, error visual con borde rojo si el código es inválido. **El botón de reenvío mejora sobre mobile**: mobile lo tiene como stub sin funcionalidad real (comentario `// Trigger resend` sin implementar); en web sí vuelve a llamar `forgotPassword` de verdad tras el contador de 60s.
- `/reset-password` — nueva contraseña + confirmación, llama a `ForgotPasswordUseCase.resetPassword` con el `otpCode` real. **Validación simplificada** para igualar a mobile: se quitó el `regex` de mayúscula/minúscula/dígito y el medidor de fortaleza que tenía la versión anterior (ni backend ni mobile los exigen, solo `min(6)`).
- Las 3 pantallas comparten el guard de "si falta `email`/`otp` en el route state, redirige a `/forgot-password`" y el mismo lenguaje visual que `LoginForm.tsx` (`loginColors`/`appColors`, mismo `inputSx`, botón píldora dorado), pero sin el hero de imagen — igual que mobile, que tampoco lo tiene en estas 3 pantallas.

**Verificado en navegador con un email real** (`g.raba29@gmail.com`): el flujo `/forgot-password` → `/verify-otp` navega correctamente mostrando el email en el subtítulo; confirmado en los logs del backend que la petición a `verify-otp` llega bien formada (`400` por código inválido — es decir, error de negocio real, no un error de deserialización por nombre de campo incorrecto, lo cual confirma que el fix de contrato `otp`→`otpCode` funciona). **No se pudo completar el flujo hasta `/reset-password` con un código real** porque este entorno no tiene acceso al inbox de email para leer el OTP verdadero — pendiente de una verificación manual futura con acceso al correo.

### Notificaciones (`NotificationsPage.tsx` + `src/presentation/components/notifications/`)
Última pantalla grande de mobile portada. Investigación clave: **mobile no tiene backend de notificaciones en absoluto** — no existe ningún endpoint/entidad/colección en `barber-flow-api` (búsqueda exhaustiva sin resultados). `NotificationScreen.tsx` de mobile es una bandeja 100% derivada del lado cliente: `notificationService.ts` computa dos tipos de notificación a partir de las citas ya cargadas en el store local, persiste el estado leído/descartado en `AsyncStorage`, sin ninguna llamada de red. Es la situación inversa a la de Reportes (ahí el contrato real existía pero nunca se conectó); acá no hay contrato que conectar — se replicó el mismo cómputo 100% cliente en web:
- **`src/shared/types/notifications.ts`** + **`src/shared/utils/notificationService.ts`**: puerto directo del algoritmo de mobile (agrupa citas de mañana en `next-day-summary`; detecta clientes sin cita futura cuya última cita fue hace ≥30 días en `delayed-client-summary`), cambiando `AsyncStorage` por `localStorage` (clave `barber_flow_notifications`).
- **`NotificationInboxContext.tsx`** (nuevo, evita colisión con el `NotificationContext.tsx` existente que en realidad es el sistema de toasts/snackbars): al montar, si el usuario está autenticado y no está en Modo Seguro bloqueado, hace un único fetch vía `AppointmentApi.getByDateRange` en una ventana de **180 días atrás a 7 días adelante** — decisión de diseño deliberada (mobile usa lo que ya esté cargado orgánicamente en su store, sin garantía real de completitud tampoco) que cubre el umbral de 30 días de sobra. Montado en `App.tsx`.
- Componentes nuevos (`NotificationsHeroCard`, `NotificationsDisabledCard`, `NotificationSection`, `NotificationItemCard`, `NotificationsEmptyState`) con el mismo lenguaje `appColors` que Reportes/Dashboard.
- **`SidebarDrawer.tsx`**: nuevo ítem "Notificaciones" (ícono de campana) entre Reportes y Configuración, con badge rojo de no-leídas; agregado a `OPERATIONAL_PATHS` (expone datos de citas/clientes, se oculta bajo Modo Seguro igual que Citas/Clientes/Reportes) y la ruta `/notifications` envuelta en `OperationalRoute`.
- **`PreferencesCard.tsx`**: el toggle de notificaciones (antes aislado en `localStorage`, con copy "todavía no está disponible en web") ahora consume `notificationsEnabled`/`setNotificationsEnabled` del nuevo contexto — es la fuente real que controla si la bandeja muestra contenido.
- **Simplificación deliberada respecto a mobile**: el botón "Abrir" de cada notificación navega a `/appointments` o `/clients` sin deep-link al día exacto (mobile navega directo al día en Calendar); agregar esa navegación por query params habría expandido el alcance más allá de lo pedido.
- Verificado end-to-end en navegador: creada una cita real para el día siguiente → apareció correctamente el resumen "Mañana" con el nombre del cliente; "Marcar todo como leído" y "Descartar" funcionan y persisten tras recargar (localStorage); badge de no-leídas correcto en el Drawer; con Modo Seguro activo `/notifications` redirige a `/dashboard`. La cita de prueba se marcó como "Cancelada" al finalizar (el formulario de citas no tiene una acción de eliminar — limitación preexistente, no introducida por este trabajo).

### Filas "Ayuda" y "Eliminar cuenta" del Drawer (`SidebarDrawer.tsx`)
Se habían omitido al portar el Drawer asumiendo que no tenían funcionalidad real detrás — **corregido tras investigar `AppDrawerContent.tsx` de mobile a fondo**: "Eliminar mi cuenta" sí tiene un backend real (`DELETE /api/users/me`, ya usado por mobile vía `authService.deleteSelf()`), y "Ayuda" es un alert informativo estático (sin backend), no un placeholder vacío.
- **`ConfirmDialogContext.tsx`**: se agregó `hideCancel?: boolean` a `ConfirmOptions` para soportar alerts de un solo botón (el "Ayuda" de mobile no tiene opción de cancelar) — cambio aditivo, no afecta los usos existentes.
- **`IAuthRepository`/`AuthApi.ts`**: nuevo método `deleteSelf()` → `DELETE /api/users/me`.
- **`SidebarDrawer.tsx`**: nuevo `ActionRow` reutilizable para las filas de la zona inferior (Ayuda, Eliminar mi cuenta condicional, Cerrar sesión). "Eliminar mi cuenta" solo se muestra si `user?.role !== 'Admin'` (mismo guard que mobile y que el propio backend, que además prohíbe la operación con `403` para el rol Admin).

**Dos bugs de backend reales encontrados y arreglados (`barber-flow-api`, `UsersApi.cs`)** — el endpoint `DELETE /api/users/me` nunca había funcionado, ni para mobile ni para nadie, contrario a lo que se asumió en el plan inicial (que atribuía el "401" documentado anteriormente a un token vencido):
1. **401 siempre**: `DeleteSelfAsync` buscaba el claim `JwtRegisteredClaimNames.NameId` ("nameid") directamente, pero ASP.NET remapea ese claim a `ClaimTypes.NameIdentifier` por defecto al validar el JWT (`DefaultInboundClaimTypeMap`), así que la búsqueda del claim literal nunca encontraba nada.
2. **500 tras el primer fix**: el token emite *dos* claims distintos ("sub" con el username y "nameid" con el Guid del usuario) que **ambos** se remapean a `ClaimTypes.NameIdentifier` — quedan coexistiendo dos claims con el mismo tipo. `FindFirst` devolvía el primero (el del username, por el orden de emisión), y `MongoDbUserRepository.DeleteAsync` fallaba con `FormatException: Unrecognized Guid format` al intentar `Guid.Parse` sobre un username. Solución: iterar todos los claims candidatos (`ClaimTypes.NameIdentifier` + `JwtRegisteredClaimNames.NameId`) y quedarse con el primer valor que efectivamente parsea como `Guid`, en vez de confiar en `FindFirst`.

Verificado end-to-end en navegador con una cuenta de Barbero de prueba (rol no-Admin): "Eliminar mi cuenta" desloguea y redirige a `/login`; un intento posterior de loguear con las mismas credenciales falla ("Autenticación fallida"), confirmando que la cuenta se eliminó de verdad y no solo del lado del cliente. **Pendiente no resuelto por este trabajo**: `DeleteSelfAsync` solo elimina el `User`, no el `Barber` asociado (quedó un perfil de Barbero huérfano tras la prueba, eliminado manualmente vía `ApplicationUsersDialog`) — si se prioriza este flujo, el backend debería borrar ambos registros en la misma operación.

Como la UI web nueva sí permite reasignar fecha **y hora**, se extendió toda la cadena para aceptar `NewTime` opcional (`string?`, se ignora si es null/vacío, así que mover solo la fecha sigue funcionando igual que antes) — DTO, interfaces, ambas implementaciones de repositorio (Mongo + InMemory) y sus tests. Verificado end-to-end: mover una cita de prueba de `11:00` a `14:30` el mismo día, confirmado con `read_network_requests` que el `PATCH` devuelve `200` y, tras recargar la página desde cero, que la hora nueva persistió de verdad (no solo visualmente).

### Validación de fecha/hora futura + anti-doble-booking al crear/mover citas
Durante la verificación de "Mover cita" se encontró que `createAppointmentSchema.date` en `src/shared/validation/appointmentSchemas.ts` tenía un bug real: comparaba `new Date(date) > new Date()`, pero `date` es solo `"yyyy-MM-dd"` (sin hora) — siempre se parsea a medianoche, así que **cualquier cita para "hoy" era rechazada sin importar la hora elegida**, porque la hora nunca entraba en la comparación. Al investigar el equivalente en mobile (`useAppointmentForm.ts`) se confirmó que mobile tenía el problema opuesto: **no validaba fecha/hora en absoluto**, permitiendo crear/mover citas a cualquier momento, incluso en el pasado. El usuario pidió arreglar ambas apps y además agregar una regla que no existía en ninguna: no permitir crear/mover una cita a un horario donde ya haya otra cita agendada (anti-doble-booking).

La regla de negocio real (fecha+hora futura, sin conflicto) se implementó en el **backend** (`barber-flow-api`), única fuente de verdad compartida por ambos clientes, y se replicó solo la validación de "futuro" en cada frontend para feedback instantáneo:

- **Backend** — `AppointmentService.cs`: nuevo método privado `EnsureScheduleIsValidAsync(date, time, excludeId, ct)` que combina fecha+hora y exige que sea estrictamente futuro, y consulta el nuevo `IAppointmentRepository.HasConflictAsync(date, time, excludeId, ct)` (implementado en `MongoDbAppointmentRepository`/`InMemoryAppointmentRepository`: existe otra cita no cancelada en esa fecha+hora exacta, excluyendo la propia en updates/moves). Se invoca en `CreateAsync` (siempre), `UpdateAsync` (**solo si `Date`/`Time` cambiaron** respecto al existing, para no bloquear marcar como Completada/Cancelada una cita ya pasada) y `MoveAsync` (siempre, usando `newDate` + `newTime ?? hora existente`). Si falla, lanza `AppointmentSchedulingException`, capturada en `AppointmentsApi.cs` (Create/Update/Move) → `400 { message }`.
- **Web** — `appointmentSchemas.ts`: se quitó el `.refine` roto del campo `date` y se agregó un `.refine` a nivel de objeto (`isFutureAppointmentDateTime`, exportado) que combina `date`+`time` antes de comparar contra `new Date()`. Se aplicó al `createAppointmentSchema` y también al `moveAppointmentSchema` (existía pero nunca estaba conectado a la UI). `AppointmentForm.tsx`: la card "Mover cita" ahora valida inline con el mismo helper antes de habilitar el botón, mostrando "La fecha y hora deben ser en el futuro" bajo los campos. El error de conflicto (doble-booking) no se duplica client-side — ya llega desde el backend vía el toast existente en `useAppointments.moveAppointment`/`createAppointment` (`showNotification('error', ...)`).
- **Mobile** — `useAppointmentForm.ts`: `validateAppointmentField` para la key `"time"` ahora también recibe la `date` del draft y valida con el nuevo helper `isFutureDateTime` (`utils/formatUtil.ts`). Como el flujo de "Mover cita" de mobile (`AppointmentFormScreen.tsx`) escribe la nueva fecha/hora directo al mismo `draft` vía `setField`, este único cambio cubre creación, edición y mover sin tocar la pantalla. Nuevas keys de localización `validation.appointmentDateTimeFuture` en `en.ts`/`es.ts`. El error de conflicto llega igual desde el backend vía el `catch` que ya tenía `handleSubmit` (`showAlert(title, getErrorMessage(error))`).

**Bug adicional encontrado y arreglado en `useForm.ts`** (afecta a todos los formularios que usan este hook, no solo Citas): `validate()` seteaba `errors` desde el `ZodError` pero nunca marcaba esos campos como `touched`, y `FormTextField` solo muestra el mensaje de error si `isTouched` es `true`. Esto significaba que un error de validación a nivel de objeto (como el nuevo de fecha+hora combinadas) en un campo que el usuario nunca tocó manualmente (p. ej. `date`, precargado por defecto) se computaba pero **nunca se mostraba** — rechazo silencioso. Se corrigió marcando como touched todos los campos presentes en `newErrors` dentro del catch de `validate()`.

Verificado end-to-end en navegador: (1) crear cita para hoy con hora futura → ahora permite (antes fallaba); (2) crear cita para hoy con hora pasada → rechazada client-side con el mensaje visible bajo Fecha; (3) crear dos citas en la misma fecha+hora → la segunda rechazada por el backend (`400`, confirmado con `read_network_requests`); (4) mover una cita a un horario ya ocupado por otra cita → rechazada (`400`), cita original no se mueve; (5) mover una cita a un horario futuro libre → funciona y persiste (confirmado tras recargar). Backend: 187 tests (`dotnet test`) en verde, incluyendo los nuevos casos de `HasConflictAsync` y de fecha/hora pasada en Create/Update/Move.

### Drawer fijo en pantallas grandes
Pedido directo, sin referencia mobile (mobile no tiene este concepto — usa bottom tabs). `SidebarDrawer` era siempre `variant="temporary"` (overlay abierto/cerrado con el hamburguesa del `AppBar`), sin importar el tamaño de pantalla. Ahora usa el patrón "responsive drawer" estándar de MUI:
- **`SidebarDrawer.tsx`**: detecta el breakpoint con `useMediaQuery(theme.breakpoints.up('md'))` (900px, default de MUI) y decide su propio `variant` (`permanent` en desktop, `temporary` por debajo) — `Router.tsx` no necesita saber en qué breakpoint está. En desktop `open` se fuerza a `true` (ignora el prop `open`, que solo importa en mobile). Se envuelve el `MuiDrawer` en `Box component="nav" sx={{ width: { md: DRAWER_WIDTH }, flexShrink: { md: 0 } }}` — necesario porque el `Paper` de un drawer permanente es `position: fixed` y no reserva espacio por sí solo; ese wrapper es lo que corre el contenido a la derecha. Se agregó `ModalProps={{ keepMounted: true }}` (mejor rendimiento en mobile, no reinstancia el DOM cada apertura). Ancho extraído a constante exportada `DRAWER_WIDTH` (antes hardcodeado `280` solo en el `PaperProps`).
- **`AppBar.tsx`**: el ícono de hamburguesa se oculta en desktop (mismo breakpoint, `useMediaQuery` propio) — no tiene función cuando el drawer está siempre visible.
- **`Router.tsx`** (`ProtectedLayout`): el contenedor raíz pasa de columna (`AppBar` arriba, contenido abajo) a un layout de dos columnas: `SidebarDrawer` a la izquierda + una columna a la derecha (`flex: 1, minWidth: 0`) con `AppBar`+`main`+`Footer` apilados como antes. Sin `useMediaQuery` aquí — toda la lógica de breakpoint vive en `SidebarDrawer`/`AppBar`.

Verificado en navegador a 1400×900 (desktop): drawer fijo visible sin clickear nada, sin ícono de hamburguesa, contenido corrido correctamente a la derecha, navegación entre secciones sin que el drawer se cierre o el contenido salte. **No verificado visualmente el comportamiento por debajo de 900px** (`resize_window` de la herramienta de automatización no cambia el viewport real en este entorno — confirmado con `window.innerWidth`, se queda fijo) — la rama `temporary` es código preexistente sin modificar (mismo `MuiDrawer` que ya funcionaba así antes de este cambio), así que el riesgo de regresión es bajo, pero vale la pena confirmarlo manualmente angostando la ventana del navegador real.

### Bug de overflow en la grilla del calendario mensual (mobile)
Probando el drawer fijo con Chrome DevTools en modo dispositivo, se reportó que en pantallas angostas los números de la grilla mensual (`AppointmentCalendarGrid.tsx`) quedaban desalineados y la última columna (domingo) salía fuera del contenedor. Causa raíz: el clásico bug de CSS Grid con `1fr` — `gridTemplateColumns: 'repeat(7, 1fr)'` usa por defecto `minmax(auto, 1fr)` por track, así que si el contenido intrínseco de una celda (un `Box component="button"` sin reset de estilos nativos de `<button>` del navegador — padding/min-width UA por defecto) es más ancho que el espacio disponible dividido entre 7, los tracks no se encogen y la grilla entera se desborda del contenedor, empujando la última columna fuera de vista. Se corrigió cambiando ambas grillas (encabezado de días + días del mes) a `repeat(7, minmax(0, 1fr))`, y se reseteó el botón de celda (`p: 0`, `m: 0`, `font: 'inherit'`, `minWidth: 0`, `width: '100%'`) para que pueda encogerse libremente sin herencia de estilos nativos del navegador. Verificado en un viewport real de 375×667 (iPhone-sized): las 7 columnas quedan parejas y el domingo permanece dentro del calendario en todas las filas.
